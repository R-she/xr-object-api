# 反思報告：用 Subagent 團隊打造 XR 物件 API

## 1. 實驗設計與量測方式

主 Agent 扮演 Tech Lead（派工、彙整、驗收），下面掛 5 個角色：
`team/architect`、`team/coder`、`team/tester`、`team/reviewer`，以及 Part B 的 `team/db-bench`（同一角色開 3 個實例並行）。

數字不是估算，是從 OpenCode 本機資料庫的 `session_v2` 讀出來的：`tokens_input/output/reasoning`、`tokens_cache_read`，
牆鐘時間取「該 session 第一次活動到最後一次活動」。全部角色使用同一個免費模型（`cost = 0`），
所以比較的是 **token 量與牆鐘時間**，不是金額。

## 2. 單一 Agent vs. 多 Subagent

Part B 是最乾淨的對照組：三個互不相依的評估，同時啟動。

| 指標 | 3 個 db-bench 並行（實測） | 序列執行（以實測耗時相加） |
| --- | --- | --- |
| 牆鐘時間 | **145 秒**（21:11:16 → 21:13:41） | **270 秒**（59 + 66 + 145） |
| 子代理耗時合計 | 270 秒 | 270 秒 |
| input tokens | 174,892 | ≈ 175k，且後兩棒會夾帶前棒的輸出 |
| output tokens | 17,970（另 reasoning 11,279） | 相同工作量 |
| cache read | 915,456 | 較少（共用同一段 context） |
| 產出 | 3 份同格式 JSON，可自動排序 | 3 份，但會互相錨定 |

並行省下約 **46% 牆鐘時間**，代價是 context 不共用：三個子代理各自重讀一次專案背景，input 不會比較少。
真正的收穫不是「快」，而是**獨立性**——三個評估互看不到對方，不會出現「第一個說 SQLite 好，後面兩個跟著附和」。

反例也很有說服力：`architect` 跑了 **1810 秒、輸出 10,412 tokens（其中 reasoning 13,472）、產出 0 個檔案**。
同一段時間，`coder` 用 254 秒就交出 9 個檔案並通過 18 條自檢。**時間長不等於產出多**，卡住的原因不是能力，是流程。

## 3. 哪個子代理表現最好／最差

**最好：`team/db-bench`（SQLite）**。它量到一半發現「批次更新數字被頁快取順序污染」，自己改成每變體 5 輪、
再加 A/B 交錯驗證重跑；最後留下可重複執行的 `bench/sqlite/bench.py` 與完整原始數據。
另外兩個 db-bench 也很誠實：本機沒有 PostgreSQL/MongoDB，就標 `measured: false`、數字填 `null`，沒有編造延遲。

**次佳：`team/tester`**。兩輪共 57 個測試函式、96 個收集案例、1.57 秒全綠、沒有用 `xfail` 逃避，
還主動列出 5 個契約模糊點（`|v|` 是分量還是長度、`q` 全空白、405 的 code…），這些回饋比「測試通過」更有價值。

**第三：`team/reviewer`**。0 blocker / 5 major，每一項都有 `檔案:行號` 與修法。
它抓到的 `extra="ignore"` 是我想不到的：PUT 把 `scale` 打成 `sclae` 會回 200，然後**默默把 scale 重設為 1**——
測試全綠、API 看起來正常，卻是無聲的資料損毀。這就是「審查與實作分離」的價值。

**最差：`team/architect`**。它在 `write` 時被 `permission.rejected: edit` 擋下，卻沒有回報，
反覆思考了 27 分鐘；直到我追問才說「內容已備好、無法落地」。三個流程問題：

1. 我沒有要求「工具被拒 → 立刻回報」，它就一直重試／空轉。
2. 我把 agent 檔從 `.opencode/agents/` 搬到 `.opencode/agents/team/`，同一個 session 中途切換角色，
   權限集可能因此不同步——**我沒有先做權限 smoke test**。
3. 我的 prompt 太開放（「先讀專案現況再動筆」），它把預算花在探索，而不是先產出最小可用版本。

補救：由 Tech Lead 直接定稿 `docs/spec.md`（架構師的內容我照樣採用它的三個提醒：PUT 重設語意、`total` 定義、排序鍵），
並在**所有**角色定義加上「工具被拒立刻停止並回報，不要換路徑硬試」。

## 4. 我調整了什麼

| 調整 | 前 | 後 | 效果 |
| --- | --- | --- | --- |
| 權限 | 每個角色都能讀，寫入靠自律 | coder 禁 `tests/`、tester 禁 `app/`、reviewer 只能寫一份報告 | 第二輪 coder 沒有偷改測試；reviewer 只回報不動手 |
| 失敗處理 | 沒規定 | 「被拒即回報」寫進 5 個角色 | 後續 db-bench/tester 遇到 shell 白名單都立刻說明，沒有空轉 |
| 輸出格式 | 自由文字 | db-bench 固定 JSON schema | 主 Agent 可直接加權排序，不用重讀三段長文 |
| 步數 | db-bench `steps: 18` | 下次設 24 | SQLite 那棒剛好卡在上限，最後的 JSON 潤稿沒做完（我手動修了兩處措辭） |
| 交接 | 靠對話 | 一律靠 `docs/spec.md`、`bench/*.json` | coder/tester 都從全新 context 起步，仍能對上契約 |

## 5. 成本

| 角色 | 牆鐘（含等待） | input | output | reasoning | 主要產出 |
| --- | --- | --- | --- | --- | --- |
| 主 Agent（Tech Lead） | 2,849 秒 | 341,110 | 40,685 | 28,228 | 派工、彙整、spec 定稿、修正 |
| architect | 1,810 秒 | 57,999 | 10,412 | 13,472 | **0 檔** |
| db-bench ×3 | 145 秒（並行） | 174,892 | 17,970 | 11,279 | 3 份 JSON + 腳本 |
| coder（兩輪） | 772 秒 | 94,632 | 19,526 | 23,548 | 9 個檔案 + 3 個 major 修正 |
| tester（兩輪） | 594 秒 | 78,575 | 17,371 | 20,791 | 57 個測試函式 / 96 案例 |
| reviewer | 187 秒 | 63,232 | 6,073 | 19,281 | 5 major / 6 minor 報告 |
| security | 179 秒 | 59,993 | 13,321 | 10,678 | OWASP 報告（3 High） |

（牆鐘含角色等待我派下一棒的閒置時間；平行比較只用 db-bench，因為三者同時啟動、連續執行。）
快取讀取累計約 1,077 萬 tokens，是長 session 的主要隱形成本；免費模型下 `cost = 0`，換成付費模型時，
**「每個子代理都重讀一次背景」**會是帳單的主因，而不是產出本身。

## 6. 如果重來一次

1. **先做權限 smoke test**：每個角色先寫一個 1 行的檔案，確認 allow/deny 真的生效，再派真任務。
2. **每個角色都要有「最小可驗收版本」**：architect 應該先交 30 行骨架，而不是一次寫完整份文件。
3. **審查與測試也要有截止步數**：reviewer 的 24 步剛好夠；tester 的第二輪應先補 SQLite parity，再補邊界。
4. **人類保留最後決策**：我改了 README 的 `--factory`、修了 `bench/sqlite.json` 的措辭、把 spec 從巢狀 scenes 改成扁平 `/objects`——
   這些都不是子代理能自己決定的，也不該由它們決定。

## 7. 結論

多 Subagent 的價值在「**可切分、不相依、格式先約定**」的任務上（Part B 三份評估並行，145 秒完成）；
有先後相依的生產線（architect → coder → tester → reviewer）不會因為拆得多就變快，**交接品質才是瓶頸**。
這次最大的教訓不是「子代理會不會寫程式」，而是：**權限與失敗回報如果沒有設計，最貴的成本是空轉，不是 token。**
